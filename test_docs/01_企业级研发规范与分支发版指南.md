# 企业级前端与服务端研发代码规范及发版门禁指南

> **版本**：v2.4.0  
> **制定部门**：技术中心架构委员会  
> **适用范围**：全员技术研发团队（前端、后端、测试、DevOps）  
> **密级**：内部公开（PUBLIC）  

---

## 1. 总体研发原则

为了保障系统长期演进的稳定性、可维护性与高合规要求，全体研发人员必须遵循以下四项核心软件工程原则：

1. **安全第一（Security by Design）**：代码架构阶段必须考虑权限校验、入参净化与敏感数据脱敏，杜绝 OWASP Top 10 常见安全漏洞。
2. **高内聚低耦合（High Cohesion, Low Coupling）**：业务模块之间严格依靠明确的 API 契约通信，避免跨域直接操作未授权的数据层。
3. **单一职责与可测性（Single Responsibility & Testability）**：每个函数与组件专注解决单一领域问题，核心逻辑单元测试覆盖率需达到 80% 以上。
4. **防御性编程（Defensive Programming）**：所有外部输入、网络 IO 及异步状态调用，必须包含严格的入参校验与异常兜底降级策略。

## 2. 凭证与机密管理安全规范（严禁明文）

机密信息泄漏属于最高等级技术安全事故，所有项目必须严格遵循以下基线：

1. **绝对禁止硬编码**：
   - 严禁在代码仓库、注释、单元测试或 Markdown 文档中硬编码任何真实账号密码、数据库口令、JWT Secret、第三方 AccessKey 及云存储私钥。
   - 所有环境敏感信息一律通过统一凭据管理中心（如 Infisical、HashiCorp Vault）或在本地通过 `.env.local` 注入。
2. **提交门禁（Pre-commit Hooks）**：
   - 客户端必须启用 `gitleaks` 或 `husky` 密钥扫描工具，提交触发前自动拦截疑似密钥的敏感文本。
3. **日志脱敏**：
   - 线上日志输出时，身份证、手机号、银行卡号及用户密码必须进行星号打码脱敏（例如：`138****1234`）。

## 3. Git 分支管理与协作流程

项目采用基于主干优化的 **Trunk-based / Git Flow** 混合协作模型：

```
main (受保护，只允许 PR 合并，自动化部署生产环境)
  │
  ├── release/vX.Y.Z (预发布分支，冻结特性，仅修复 P0 缺陷)
  │
  └── feature/xxx (特性开发分支，源自最新 main)
```

### 3.1 分支命名规范
- **新功能**：`feature/JIRA-编号-模块简述`（如：`feature/DOC-102-r2-upload`）
- **缺陷修复**：`fix/JIRA-编号-问题简述`（如：`fix/DOC-108-ssl-handshake`）
- **紧急热修复**：`hotfix/版本号-线上问题简述`（如：`hotfix/v2.3.1-jwt-expire`）

### 3.2 提交说明格式（Conventional Commits）
提交信息统一遵循规范格式：`<type>(<scope>): <subject>`，例如：
- `feat(document): 支持从本地拖拽直传 Cloudflare R2 并生成预签名链接`
- `fix(auth): 修复 Node 22 环境下由于时序加载导致的数据库连接失败问题`
- `docs(api): 更新知识库管理模块对外 OpenAPI 文档`

## 4. 自动化流水线（CI/CD）发版门禁

所有合并至 `main` 分支的代码必须通过以下自动化流水线检查（Gateways）：

1. **静态代码分析与 Lint 检查**：
   - ESLint / Prettier 零错误通过。
   - TypeScript 编译无隐式 `any`（`noImplicitAny: true`）。
2. **自动化测试套件**：
   - 单元测试（Unit Tests）全部通过。
   - 核心链路集成测试（E2E / Integration Tests）无失败用例。
3. **人工代码审查（Code Review）**：
   - 至少需要一位同组资深架构师或 Tech Lead 评审通过（`Approved`）并留下评审意见方可执行合并。
4. **灰度发布与回滚预案**：
   - 生产环境发布严格遵循灰度比例（`10% -> 30% -> 100%`）。
   - 上线后观测监控告警指标 15 分钟，若 5xx 错误率超过 0.5%，立即自动触发金丝雀一键回滚。
