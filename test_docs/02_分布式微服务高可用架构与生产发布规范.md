## 1. 架构总则与微服务拆分基线

### 1.1 总体架构愿景
本规范旨在保障集团各核心业务系统达到 **99.99%（四个九）** 的年度高可用性目标，杜绝单点故障（SPOF），确保高并发峰值冲击下的系统弹性收缩与故障快速止血恢复能力。

### 1.2 微服务拆分四项硬性准则
1. **单一业务职责（Single Responsibility）**：依据领域驱动设计（DDD）界定限界上下文（Bounded Context），严禁横向交叉包含多套独立业务主数据。
2. **数据独立私有化（Database-per-Service）**：每个微服务必须拥有独立私有的数据库实例或 Schema，**严禁跨服务直接通过 SQL Join 访问其他服务的业务数据库**，跨服务数据交互必须统一经由 RPC 或 HTTP RESTful API 契约协议调用。
3. **无状态化计算节点（Stateless Architecture）**：应用层 Pod/容器必须做到完全无状态，用户会话、临时状态必须外置沉淀至 Redis 集群，确保 Pod 在遇到硬件故障、节点迁移或 HPA 自动水平扩缩容时可随时销毁与冷启动。
4. **强弱依赖解耦与优雅降级**：
   - 核心链路（如登录、支付、文档审批主干）必须识别出非核心弱依赖（如短信通知、积分累计、审计日志、推荐卡片）；
   - 弱依赖发生超时或宕机时，主调用链必须有熔断降级（Fallback）兜底，绝不允许弱依赖拖垮整个主服务集群。

## 2. 服务间调用与异步消息解耦规范

### 2.1 同步 RPC 与 HTTP 调用规范
1. **超时时间（Timeout）硬性约束**：
   - 内部服务间点对点调用必须显式设置超时时间，默认读取超时建议 `3000ms`，极限不得超过 `5000ms`，禁止使用无限制阻塞；
   - 对外公共网关（Gateway）下游反向代理单次 HTTP 超时时间不得超过 `10s`。
2. **重试机制与幂等性（Idempotency）**：
   - 只有**只读接口（GET/HEAD）**或具备**显式幂等机制**的写入接口方可配置自动重试，重试次数建议为 2 次，并配合指数退避（Exponential Backoff）策略；
   - 涉及金融扣款、库存核减、审批状态变更的写接口，必须在服务提供方通过分布式锁（Redlock）或唯一业务幂等流水号（Idempotent Key）做防重校验，防止网络抖动导致的重复开销。
3. **断路器机制（Circuit Breaker）**：
   - 当某下游依赖在滑动窗口 60 秒内错误率超过 50% 或慢调用比例超 60% 时，熔断器必须自动跳闸切断流量，直接返回降级 Mock 响应或友好兜底文案，并在 15 秒试探期（Half-Open）健康后方可自动恢复闭合。

### 2.2 消息队列（RabbitMQ / Kafka）设计规范
1. **交换机与队列命名空间**：
   - 格式标准：`<业务线>.<核心实体>.<事件动作>.<类型>`，例如：
     - `kh.doc.approval.topic`（知识库文档审批主题交换机）
     - `kh.doc.index.vector.queue`（文档向量化切片消费队列）
     - `kh.doc.index.es.queue`（文档全文检索倒排索引消费队列）
2. **可靠消费与死信补偿机制（DLX）**：
   - 生产端必须启用发布者确认机制（Publisher Confirms）；
   - 消费端严禁使用 `autoAck=true`，必须在数据完全落地、衍生状态持久化成功后，才显式向 Broker 发送 `basicAck`；
   - 消费失败应重试 3 次，若依然发生未捕获异常，消息必须由 Broker 自动路由转发至绑定的死信队列（Dead-Letter Queue, DLQ），同时触发告警通知由补偿任务人工介入修复。

## 3. 分布式缓存与持久层优化规范

### 3.1 Redis 缓存防击穿、防穿透与防雪崩军规
1. **防缓存穿透（Cache Penetration）**：
   - 查询数据库不存在的无效 Key 时，必须向 Redis 写入空值占位符（如 `EMPTY_PLACEHOLDER`），并配置较短的过期时间（60 ~ 180 秒）；
   - 大流量高频查询必须在服务接入层前置引入**布隆过滤器（Bloom Filter）**，在内存中直接拦截非法非法 ID 请求。
2. **防缓存击穿（Hot-key Invalidation）**：
   - 针对高频访问的热点核心数据（如首页配置、系统全局枚举、热门置顶文档），严禁设置相同的自然整点过期时间；
   - 在后台采用异步工作线程（Cron Job）对热点缓存实行主动刷新（Cache Warm-up），或采用分布式互斥锁避免大量并发直接击穿至 MySQL。
3. **防缓存雪崩（Cache Avalanche）**：
   - 所有写入 Redis 的缓存 Key，过期时间必须附加一定范围的随机抖动值（Random Jitter），如：`base_ttl (3600s) + random(0, 600s)`，避免同一时段集中失效导致持久层雪崩。
4. **禁止 Keys 操作与大 Key 限制**：
   - 生产环境严禁使用 `keys *` 指令，全量扫描必须使用 `SCAN` 分页游标；
   - 单个 String 类型的 Key 大小不得超过 `100KB`；Hash/Set/ZSet 集合元素数量不得超过 `5000` 个。

### 3.2 关系型数据库（MySQL / PostgreSQL）设计准则
1. **索引规范**：
   - 单表索引总数不得超过 6 个，遵循最左前缀匹配原则；
   - 避免在低基数（如性别、状态标志）字段上单独建立普通单列索引；
   - 严禁在代码中写出 `SELECT *`，必须显式指明需要查询的字段名，尽可能利用覆盖索引减少回表 IO 开销。
2. **大表归档与分页优化**：
   - 单表数据量预计超过 1000 万行或物理存储超 20GB 时，需在立项设计时提供分库分表或历史冷数据归档方案；
   - 严禁使用深分页语法（如 `LIMIT 100000, 20`），分页查询必须利用自增 ID 寻址（`WHERE id > last_seen_id LIMIT 20`）。

## 4. 生产环境发版流水线与部署红线

### 4.1 发版时间窗口规定
- **常规发布窗口**：每周二、周四上午 **10:00 ~ 11:30** 或下午 **14:30 ~ 16:30**；
- **发版封锁期（Freeze Window）**：
  - 严禁在周五下午、节假日以及重要节假日前一天下班前进行任何生产环境变更；
  - 遇到集团大促活动或全网营销活动期间，提前 48 小时执行全局代码封版（Code Freeze）。

### 4.2 渐进式金丝雀发布（Canary Deployment）标准
生产发布必须通过 Kubernetes Ingress 严格执行阶梯权重分流：
1. **阶段一（灰度 5% 流量）**：金丝雀版本上线，观测 15 分钟，核查错误日志、HTTP 5xx 占比与 JVM/Node 内存曲线；
2. **阶段二（放量 20% 流量）**：继续放量，运行 30 分钟，进行真实用户链路抽样；
3. **阶段三（全量 100% 切换）**：全网切流，保留旧版本 Pod 处于就绪待命状态 1 小时，确保秒级回滚能力。

### 4.3 生产发布三大熔断回滚红线
在发版过程中，一旦触发下列任一条件，发布流水线必须立即无条件**一键回滚（Rollback）**至上一个稳定版本：
1. 全局系统接口 HTTP 5xx 错误率在 3 分钟内持续超过 **1%**；
2. 核心链路接口 P99 响应耗时（Latency）较发版前基准值恶化上浮超过 **50%**；
3. 数据库连接池耗尽、死锁日志报警或服务容器频繁发生 OOMKilled 重启。

## 5. 生产可观测性（Observability）建设要求

所有纳管到生产环境的服务必须完整支持可观测性“三支柱”：
1. **指标体系（Metrics）**：基于 Prometheus 统一输出四大黄金指标（延迟 Latency、流量 Traffic、错误 Errors、饱和度 Saturation）；
2. **结构化日志（Logs）**：统一输出 JSON 格式日志，必须全链路透传追踪标识 `trace_id` 与 `span_id`，禁止打印多行无格式明文异常栈；
3. **分布式链路追踪（Traces）**：基于 OpenTelemetry 协议埋点，实现从 API 网关 -> 业务微服务 -> MQ -> 数据库/缓存的全程可视化调用链耗时分析。
