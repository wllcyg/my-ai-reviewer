# Nest 业务后端与 Python AI 服务交互设计文档

Nov 2, 2026 · @wl

## 1. 概述

本文定义业务后端（Nest，基于 nest-admin）与 AI 服务（Python）的交互方式：文档处理走异步队列，在线问答走同步流式，所有对外入口只经过 Nest。

**背景**：业务后端用 nest-admin，AI 侧的文档处理（解析、切块、向量化）用 Python。两者技术栈不同，后端将来也可能换成 Java 或 C#，所以通信契约必须与语言无关。

**目标**

- 两个系统只通过明确的契约通信，任何一侧改实现，不影响另一侧。
- 耗时的文档处理不阻塞业务请求，任务不丢、可重试、可追踪。
- 一侧故障时影响范围可控，能自动恢复，事后能查清原因。

**范围**

- 包含：文档处理通道、在线问答通道、任务表、消息协议、内部接口、可靠性、部署与监控建议。
- 不包含：前端交互细节、RAG 检索效果调优、向量库与模型选型。

**术语**

| 术语 | 含义 |
| --- | --- |
| Nest | 业务后端，唯一对外入口，业务库的唯一写入方 |
| AI 服务 | Python 服务，包含 HTTP 服务（问答）与 worker（文档处理） |
| 任务（task） | 一次文档处理，用 taskId 标识 |
| 任务表 | Nest 业务库中的 doc\_task 表，任务状态的唯一事实来源 |
| 通知队列 | 只负责把 taskId 通知给 worker，不作为状态来源 |

## 2. 总体架构与职责划分

原则是 Nest 管业务、Python 管 AI，每份数据只有一个写入方，两边通过契约和队列通信，不共享数据库表。

| 组件 | 负责 | 不负责 |
| --- | --- | --- |
| Nest（nest-admin） | 登录鉴权、权限、限流、文档与任务管理、会话记录、对前端的唯一入口、业务库读写 | 文档解析、向量化、检索与生成 |
| AI 服务（Python HTTP） | 在线问答：检索、拼提示词、调用模型、流式返回 | 对外暴露、用户鉴权、业务库读写 |
| AI worker（Python） | 消费任务消息，完成下载、解析、切块、向量化、入库，回调 Nest | 对外暴露、直接写业务表 |
| 通知队列 | 投递 taskId 通知，保证 worker 能取到 | 保存任务状态、保存文件内容 |
| 对象存储 | 存原始文档与解析中间产物 | 业务逻辑 |
| 向量库 | 存切块后的向量与元数据 | 业务数据 |

**数据归属**

- 业务库（用户、文档、任务、会话）：只由 Nest 写，Python 通过回调接口提交结果。
- 向量库与解析中间产物：只由 Python 写，Nest 不直接读，需要时通过 AI 服务接口获取。
- 消息里只传标识（taskId、fileId），不传文件内容。

**网络边界**

- 只有 Nest 面向公网，AI 服务与 worker 只开放内网，Nest 调用 AI 服务时带服务间令牌。
- 所有组件部署在同一地域内网（首尔），避免跨境调用。

## 3. 通信方式总览

按交互类型分两条通道：耗时且可重试的文档处理走异步队列，需要即时反馈的问答走 HTTP 加 SSE，Nest 始终是入口。

| 维度 | 通道 A：文档处理 | 通道 B：在线问答 |
| --- | --- | --- |
| 特点 | 耗时几秒到几分钟，可重试，不要求实时 | 要求低延迟，逐字流式输出 |
| 方式 | 队列通知加回调 | Nest 调 AI 服务，HTTP 加 SSE |
| 发起方 | Nest 投递，worker 消费 | Nest 发起，AI 服务流式响应 |
| 状态来源 | Nest 的任务表 | 请求生命周期内，会话记录由 Nest 写 |
| 失败处理 | 重试、死信、补偿扫描 | 超时、提示用户重试，不自动重放 |

**为什么不让前端直连 Python**：鉴权、限流、配额、审计会拆成两份，长期维护成本高，也会把 AI 服务暴露到公网。

**为什么不用同步 HTTP 做文档处理**：长请求容易超时，服务重启会丢失，也没法削峰。

**契约管理**：AI 服务的 HTTP 接口用 OpenAPI 描述，Nest 侧由它生成类型化客户端，接口变更在编译期暴露；队列消息用 JSON，带 schemaVersion。

## 4. 文档处理流程（异步）

一次文档处理由 Nest 建任务并投递，worker 领取后分阶段处理并回调，任务表始终记录最新状态。

图中左右箭头是 worker 对 Nest 回调接口的调用；队列里只有标识，任务状态的每次变化都由 worker 回调 Nest 后写入任务表。队列或 worker 出问题时，Nest 的补偿扫描按任务表重新投递（虚线）。

**处理阶段**

1. download：从对象存储下载文件。
2. parse：解析文本与结构。
3. chunk：切块。
4. embed：调用向量化，最慢，也最容易受外部接口影响。
5. store：写入向量库。

每个阶段结束都上报 progress，失败时能知道卡在哪一步，并从该阶段重试。

**状态流转**

- pending 到 processing：worker 调 claim 成功。
- processing 到 done：worker 调 complete。
- processing 到 failed：worker 调 fail，或超过最大重试次数。
- pending 或 processing 到 canceled：用户取消，worker 在阶段边界检查并停止。
- processing 超时：补偿扫描重新投递，状态回到 pending，attempt 加 1。

**前端看进度**

前端向 Nest 轮询任务状态，或订阅 Nest 提供的 SSE；进度数据只来自任务表，前端不直接接触队列或 AI 服务。

## 5. 消息协议

消息体用 JSON，只放标识和少量元数据，不放文件内容，不使用任何语言专属的序列化格式。

**队列命名**

| 名称 | 用途 |
| --- | --- |
| doc.process | 文档处理任务通知 |
| doc.process.retry | 延迟重试（按需） |
| doc.process.dead | 死信：反复失败的消息，等待人工处理 |

**消息体字段**

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| schemaVersion | int | 是 | 消息格式版本，当前为 1 |
| taskId | string | 是 | 任务唯一标识，幂等依据 |
| type | string | 是 | 任务类型，如 doc.parse |
| fileId | string | 是 | 对象存储中的文件标识 |
| docId | string | 否 | 业务库中的文档 ID |
| attempt | int | 是 | 当前第几次投递，从 1 开始 |
| traceId | string | 是 | 全链路日志追踪标识 |
| createdAt | string | 是 | 投递时间，ISO 8601 |

**示例**

```json
{
  "schemaVersion": 1,
  "taskId": "t_01HXYZ...",
  "type": "doc.parse",
  "fileId": "f_8a31...",
  "docId": "d_1024",
  "attempt": 1,
  "traceId": "tr_77c2...",
  "createdAt": "2026-11-02T14:00:00+08:00"
}
```

**版本策略**

- 新增字段只加可选字段，旧 worker 忽略不认识的字段。
- 删除或改变字段含义时升 schemaVersion，新旧版本并存一段时间后再下线旧版本。
- worker 遇到不认识的 schemaVersion，不处理，直接进死信队列并告警。

## 6. 任务表设计

任务表 doc\_task 是任务状态的唯一事实来源，队列丢消息时，靠它补偿恢复。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | string | 主键，即 taskId |
| doc\_id | string | 关联文档 |
| file\_id | string | 对象存储中的文件标识 |
| type | string | 任务类型 |
| status | string | 状态，见下表 |
| stage | string | 当前阶段：download / parse / chunk / embed / store |
| progress | int | 0 到 100 |
| attempt | int | 已投递次数 |
| error\_code | string | 失败原因码，成功时为空 |
| error\_msg | string | 失败原因摘要 |
| trace\_id | string | 全链路追踪标识 |
| created\_at | datetime | 创建时间 |
| updated\_at | datetime | 最近一次状态或进度更新，补偿扫描依据 |
| finished\_at | datetime | 结束时间 |

**状态定义**

| 状态 | 含义 | 谁来改 |
| --- | --- | --- |
| pending | 已建任务，待投递或已投递未被领取 | Nest |
| processing | worker 已领取，正在处理 | Python 经回调 |
| done | 处理成功 | Python 经回调 |
| failed | 超过最大重试次数或不可重试错误 | Python 经回调 或 Nest 补偿 |
| canceled | 用户取消 | Nest |

**索引建议**

- (status, updated\_at)：补偿扫描用。
- (doc\_id)：按文档查任务。

**补偿扫描规则**

- 每分钟扫描一次。
- pending 且 updated\_at 早于 5 分钟：重新投递，attempt 加 1。
- processing 且 updated\_at 早于 10 分钟（worker 应定期刷新 updated\_at）：视为 worker 已挂，重新投递。
- attempt 超过 3：置为 failed，写入 error\_code，并告警。
- 以上时间阈值是初始建议，上线后按文档实际处理时长调整。

**一致性写法**

建任务记录与投递消息要避免“库里写了、消息没发出去”：先写任务表（pending），再投递；投递失败时保持 pending，由补偿扫描兜底。需要更严格时用 Outbox：任务记录与待发消息在同一事务写入，由后台进程转发。

## 7. 内部接口

两个方向各一组内部接口，都只在内网开放，请求头带服务间令牌，路径前缀统一为 /internal。

**7.1 Nest 提供给 Python 的回调接口**

| 方法与路径 | 用途 |
| --- | --- |
| POST /internal/tasks/{taskId}/claim | worker 领取任务，原子地把 pending 改为 processing，已被领取则返回 409 |
| POST /internal/tasks/{taskId}/progress | 上报阶段与进度，同时刷新 updated\_at |
| POST /internal/tasks/{taskId}/complete | 上报成功，带结果摘要 |
| POST /internal/tasks/{taskId}/fail | 上报失败，带错误码与是否可重试 |

进度上报请求示例：

```json
POST /internal/tasks/t_01HXYZ/progress
{
  "stage": "embed",
  "progress": 60,
  "attempt": 1
}
```

失败上报请求示例：

```json
POST /internal/tasks/t_01HXYZ/fail
{
  "errorCode": "PARSE_ERROR",
  "errorMsg": "unsupported pdf encryption",
  "retryable": false
}
```

回调接口都要幂等：对已经是 done、failed、canceled 的任务重复上报，返回成功但不改变状态。

**7.2 Python 提供给 Nest 的接口**

| 方法与路径 | 用途 |
| --- | --- |
| POST /internal/chat/stream | 在线问答，SSE 流式返回，见第 8 章 |
| POST /internal/docs/{docId}/delete-vectors | 删除某文档的向量数据，文档被删除时调用 |
| GET /internal/health | 健康检查，供部署与监控使用 |

**7.3 统一错误响应**

```json
{
  "code": "TASK_NOT_FOUND",
  "message": "task does not exist",
  "traceId": "tr_77c2..."
}
```

| code | HTTP | 含义 | 调用方处理 |
| --- | --- | --- | --- |
| UNAUTHORIZED | 401 | 服务间令牌缺失或无效 | 检查配置，不重试 |
| TASK\_NOT\_FOUND | 404 | 任务不存在 | 不重试，告警 |
| TASK\_ALREADY\_CLAIMED | 409 | 已被其他 worker 领取 | 放弃本次消息并 ack |
| INVALID\_STATE | 409 | 当前状态不允许该操作 | 按幂等处理，记录日志 |
| RATE\_LIMITED | 429 | 被限流 | 退避后重试 |
| INTERNAL\_ERROR | 500 | 服务内部错误 | 带退避重试，上限 3 次 |

**调用约定**

- 所有跨服务调用设超时：回调接口 5 秒，连接超时 2 秒。
- 可重试错误用指数退避加随机抖动，初始建议 1 秒，上限 3 次。
- 每个请求带 X-Trace-Id，日志里打印，用于串联两边的日志。

## 8. 在线问答（同步流式）

问答走 Nest 到 AI 服务的 HTTP 加 SSE：Nest 负责鉴权、限流与会话记录，AI 服务负责检索与生成，结果由 Nest 转发给前端。

**请求**

```json
POST /internal/chat/stream
Authorization: Bearer <服务间令牌>
X-Trace-Id: tr_77c2...
{
  "sessionId": "s_501",
  "question": "报销流程是什么？",
  "docIds": ["d_1024"],
  "history": []
}
```

**SSE 事件**

| event | data | 含义 |
| --- | --- | --- |
| meta | { messageId } | 流开始，返回消息标识 |
| token | { text } | 一段生成文本，前端按顺序拼接 |
| source | { docId, chunkId, score } | 引用来源，可出现多次 |
| error | { code, message } | 出错，之后流结束 |
| done | { usage } | 正常结束，带用量信息 |

**约定**

- 首个 token 的超时 15 秒，整体最长 120 秒，初始建议值，按模型实际速度调整。
- 前端断开时，Nest 同步断开到 AI 服务的连接，AI 服务检测到断开后停止生成，避免浪费调用。
- Nest 在流结束时，把完整回答与引用来源写入会话记录；中途出错时，记录已生成部分并标记未完成。
- 反向代理（如 Nginx）要关闭对该路径的响应缓冲，否则流会被攒成一次性返回。
- 问答失败不自动重放，由用户重新提问，避免重复计费和重复记录。

## 9. 队列选型与演进

上线初期用轻量方案，队列访问封装成薄接口，量级和可靠性要求上来后再换 RabbitMQ，换的只是封装层。

| 方案 | 适合阶段 | 优点 | 注意点 |
| --- | --- | --- | --- |
| 本地 Docker RabbitMQ | 学习与开发 | 带管理后台，可直观看消息变化，无额度和网络限制 | 只用于开发环境 |
| Redis Streams | 上线初期 | nest-admin 通常已依赖 Redis，无需新增组件，占用小 | 开启 AOF；配合任务表补偿 |
| Cloudflare Queues 免费版 | 过渡 | 不占本机内存，支持 HTTP 发布与拉取 | 免费版消息只保留 24 小时，每日操作数有限，非 AMQP |
| CloudAMQP 免费实例 | 过渡与练习 | 标准 AMQP，换成自建 RabbitMQ 零改造 | 共享实例，限额小，机房位置需核对 |
| 自建或托管 RabbitMQ | 量大后 | 路由、死信、延迟、持久化更完善 | 多一个组件要运维；国内云托管版需与服务同云同地域 |

以上免费额度与限制来自公开资料与第三方文章，选用前请到官网核对最新数据。

**薄封装接口**

```typescript
interface TaskQueue {
  publish(queue: string, message: TaskMessage): Promise<void>;
  consume(queue: string, handler: (msg: TaskMessage) => Promise<void>): void;
}
```

Python 侧同样提供 publish 与 consume 两个函数。业务代码只依赖这个接口，连接地址和凭证走环境变量。

**换实现的检查项**

- 消息格式不变（第 5 章）。
- 任务表与补偿逻辑不变。
- 只替换封装层与部署配置，并在测试环境跑通一轮完整任务。

## 10. Worker 设计

worker 一次只处理少量任务，处理期间保持连接心跳，用 taskId 保证重复消费不出错。

**处理流程**

1. 收到消息，校验 schemaVersion 与必填字段，不合法进死信并告警。
2. 调用 claim 接口领取任务：返回 409 说明已被处理，直接 ack 丢弃本条消息。
3. 按阶段执行：下载、解析、切块、向量化、入库；每完成一个阶段调用 progress 接口，同时刷新 updated\_at。
4. 全部成功调用 complete，失败调用 fail，并按 retryable 决定是否进入重试。
5. 收尾后 ack。

**并发与资源**

- 每个 worker 进程 prefetch\_count 设为 1，保证一条处理完再领下一条。
- 想同时处理 N 条，就启动 N 个进程，而不是在一个进程里堆线程；解析 PDF 这类 CPU 密集任务，多进程比多线程合适。
- 2 核 2G 的机器从 1 个进程起步，按实测的峰值内存再增加。
- 向量化阶段主要在等外部接口，可单独做异步并发，不与解析阶段共用并发配置。

**心跳与 ack**

- 耗时处理放到工作线程或子进程，连接所在的主线程只负责收发网络事件和心跳，不被长任务占住。
- 采用 pika 时，ack 必须回到连接所在线程执行（用 add\_callback\_threadsafe），不要在工作线程里直接 ack。
- 采用 aio-pika 时，CPU 密集部分放进进程池，避免阻塞事件循环，否则心跳同样会断。
- 处理完成后再 ack；若采用“先 ack 再回调”，必须保证补偿扫描已上线，并自行控制并发，避免一次领入过多任务。
- 服务端的消费者确认超时（consumer\_timeout）随版本不同，需查所用版本文档，任务可能超过该时间时要调大或拆小。

**幂等**

- 以 taskId 为幂等键：claim 接口保证同一任务只被一个 worker 处理。
- 向量入库用 docId 加 chunk 序号做确定性主键，重跑时覆盖而不是新增。
- 任何阶段都应能安全地重复执行。

**重试**

- 可重试错误（网络超时、外部接口 5xx）：退避后重新投递，attempt 加 1，上限 3 次。
- 不可重试错误（文件损坏、格式不支持）：直接 fail，不重试。
- 超过上限：进入死信队列，等待人工处理。

## 11. 可靠性与容错

设计假设是对方一定会出错：任务状态以任务表为准，队列只做通知，任何一环失败都有兜底，且影响范围不扩散。

**故障场景与处理**

| 场景 | 现象 | 处理 |
| --- | --- | --- |
| 队列服务宕机 | Nest 投递失败，worker 连不上 | 任务保持 pending，worker 带退避重连；队列恢复后补偿扫描补投 |
| 队列丢了部分消息 | 任务一直停在 pending | 补偿扫描按 updated\_at 重新投递 |
| worker 处理中崩溃 | 任务停在 processing，updated\_at 不再变化 | 补偿扫描判定超时，重新投递，worker 按幂等重跑 |
| worker 重复消费 | 同一任务被处理两次 | claim 接口只放行一个；入库用确定性主键覆盖 |
| Nest 暂时不可用 | worker 回调失败 | 带退避重试；超过上限则保留结果，待 Nest 恢复后补报或由补偿扫描收敛 |
| AI 服务不可用 | 问答请求失败 | 超时后向用户返回明确提示；连续失败时 Nest 暂时熔断，返回降级提示 |
| 外部模型接口变慢或限流 | 向量化阶段耗时拉长 | 限制向量化并发，退避重试；队列堆积时告警 |
| 消息格式不认识 | worker 无法解析 | 进入死信队列并告警，不无限重试 |
| 机器内存不足 | 进程被系统杀掉 | 限制并发与单任务内存；配置 swap 兜底；进程由守护程序自动拉起 |

**保护措施**

- 超时：所有跨服务调用都设连接与读取超时，没有无限等待。
- 重试：指数退避加随机抖动，设上限，避免重试风暴。
- 熔断与降级：Nest 调 AI 服务连续失败时，短时间内不再调用，返回降级结果后再试探恢复。
- 限流：Nest 入口按用户和接口限流；上传大小、并发处理数设上限。
- 背压：队列长度超过阈值时，Nest 暂停接收新的处理请求或提示稍后再试。
- 死信：反复失败的消息单独存放，提供查看与手动重投的入口。

**恢复与回滚**

- 所有消息格式变更向后兼容，先上线消费者，再上线生产者。
- 部署采用先小范围、再全量，出问题可快速回滚到上一个版本。

## 12. 安全与鉴权

AI 服务不暴露公网，只认 Nest 签发的服务间令牌；所有凭证走环境变量或密钥管理，不进代码仓库。

- **用户鉴权**：全部在 Nest 完成，Python 不处理用户登录，也不信任前端传来的用户身份；需要用户信息时由 Nest 在请求体里传必要字段。
- **服务间认证**：Nest 调 AI 服务、worker 调 Nest 回调接口，都带 Authorization 令牌；令牌定期轮换，两个方向使用不同的令牌。
- **网络隔离**：AI 服务与 worker 只监听内网地址，防火墙只放行 Nest 所在机器；回调接口同样不对公网开放。
- **队列凭证**：队列的连接账号只授予所需队列的读写权限；使用云端队列时，API 令牌只给 Queues 相关权限。
- **文件访问**：对象存储用预签名地址或服务账号，不开放公共读；消息里只有 fileId，不含可直接访问的地址。
- **日志脱敏**：日志里不打印令牌、文档正文与用户个人信息，只记录 taskId、docId、traceId。
- **输入校验**：Nest 校验上传文件类型与大小；worker 对解析的文件做超时与资源限制，防止恶意或超大文件拖垮机器。
- **合规**：服务部署在海外（首尔）时，若涉及公司业务数据或国内用户个人信息，需与公司法务或信息安全部门确认跨境数据要求，再决定数据与队列的存放位置。这一点不能靠技术手段绕开。

## 13. 部署与资源

现有首尔机器是 2 核 2G，内存已占用约 1041MB，只够放业务与队列的轻量部分，文档处理量上来后要拆机或升配。

**现状（来自监控截图）**

| 项目 | 数值 | 判断 |
| --- | --- | --- |
| CPU | 2 核，使用约 2.4% | 宽松 |
| 内存 | 2GB，已用约 1041MB | 紧张，是唯一瓶颈 |
| 系统盘 | 13.5GB / 50GB | 宽松 |
| 流量包 | 572MB / 1024GB | 宽松 |

**分阶段部署建议**

| 阶段 | 部署方式 |
| --- | --- |
| 学习与开发 | 本地 Docker 起 RabbitMQ 与 Python worker，不占用服务器 |
| 上线初期 | 现有机器放 Nest 与 Python 服务；队列用云端免费队列或 Redis Streams，不在这台机器上加 RabbitMQ；worker 单进程，并发为 1 |
| 文档量增长后 | Python worker 单独一台，或机器升配到 4G 及以上；队列再考虑自建或托管 RabbitMQ |

**上线前需要做的事**

- 用 docker stats 或 free -h 查清现有 1GB 内存具体是哪些服务占用，看能否瘦身。
- 配置约 2G 的 swap 作为兜底，防止瞬时峰值触发 OOM；它只能救急，不能当内存用。
- 用真实的大文档实测 Python 单任务的峰值内存，据此决定并发数与是否拆机。
- 给容器设置内存上限，避免一个服务抢占全部内存。
- 所有组件配置自动重启（如 Docker 的 restart 策略或 systemd），并设置健康检查。
- 把 Nest、Python 与队列放在同一内网与地域，对象存储也选就近地域。

**配置约定**

连接地址、令牌、并发数、超时时间都走环境变量，不同环境（开发、测试、生产）只改配置，不改代码。

## 14. 监控、日志与排障

上线前至少盯三样：队列积压、任务失败率、处理耗时，并用 traceId 把两个服务的日志串起来。

**核心指标与告警**

| 指标 | 来源 | 告警条件（初始建议） |
| --- | --- | --- |
| 队列积压数 | 队列管理界面或命令 | 持续 10 分钟高于 50 条 |
| 任务失败率 | 任务表统计 | 1 小时内失败占比超过 10% |
| 单任务处理耗时 | 任务表 finished\_at 减 created\_at | 超过平时的 3 倍 |
| 卡住的任务数 | 任务表 processing 且 updated\_at 超时 | 大于 0 |
| 死信队列消息数 | 死信队列 | 大于 0 |
| 机器内存 | 云监控或系统监控 | 使用率持续高于 85% |
| AI 服务问答失败率与首字延迟 | Nest 侧埋点 | 失败率超过 5%，或首字延迟持续超过 15 秒 |

具体阈值是起点，上线后按实际数据调整。

**日志约定**

- 所有日志用结构化格式（JSON），固定字段：时间、级别、服务名、traceId、taskId、阶段、耗时。
- Nest 创建任务时生成 traceId，写入消息，worker 与回调请求都带上它；问答请求由 Nest 生成并通过 X-Trace-Id 传给 AI 服务。
- 日志不含令牌、文档正文与个人信息。

**排障路径**

1. 用户反馈某文档处理不了：按 docId 查任务表，看 status、stage、error\_code。
2. 状态为 pending 很久：检查队列是否连通、是否有积压，补偿扫描有没有在跑。
3. 状态为 processing 很久：用 taskId 与 traceId 查 worker 日志，看卡在哪个阶段，是否内存不足被杀。
4. 状态为 failed：看 error\_code；在死信队列里的消息，修复原因后手动重投。
5. 问答变慢或失败：先看 Nest 到 AI 服务的耗时与错误，再看 AI 服务内部检索与模型调用的耗时。

**工具**

- RabbitMQ 自带管理界面，可看消息积压、未确认数与速率；使用 Redis Streams 时用 RedisInsight 查看消息与未确认列表。
- 上线后想要历史曲线与告警，可加 Prometheus 与 Grafana，但它们占内存，不要放在 2G 的业务机器上。

## 16. 待确认事项与风险

开工前要先定下面几件事，它们会改变队列选型、并发配置与部署方式。

**待确认事项**

- [ ] 单个文档的处理耗时与阶段划分：决定单队列加任务内分阶段，还是拆成多队列。
- [ ] 首尔机器上现有服务的内存占用明细：决定队列放哪、worker 能开几个。
- [ ] 数据是否涉及跨境合规：决定数据、队列与对象存储的存放位置。
- [ ] 前端进度展示用轮询还是 SSE。
- [ ] 队列正式选哪一个：Redis Streams、云端免费队列，还是尽早自建 RabbitMQ。
- [ ] 对象存储用哪家、放哪个地域。
- [ ] 后端是否确定会换语言：影响是否要尽早上 AMQP 方案。
- [ ] 云端免费队列的当前额度与机房位置，以官网为准。

**风险**

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 2G 内存被文档解析撑爆 | worker 或整台机器被杀 | 并发为 1，限制单任务内存，配置 swap，必要时拆机或升配 |
| 免费队列限额或保留期不够 | 积压消息过期或被拒 | 任务表补偿兜底；量大后迁移到自建队列 |
| 队列丢消息 | 任务停在 pending | 补偿扫描与幂等 |
| 长任务导致连接心跳断开 | 消息被重复投递 | 工作线程保心跳，处理完再 ack，幂等兜底 |
| 跨境合规未确认 | 上线后被要求整改 | 开工前与法务或信息安全部门确认 |
| 免费云服务条款变动 | 队列不可用 | 薄封装接口，随时可换实现 |
